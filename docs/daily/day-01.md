## 실험 기록

- 실제 수행일: 2026-11-11 재개. 아래는 대화 요약이며 출력·지연 관찰은 사용자 보고다.
- 질문 / 가설: 호출 위치에 따른 Promise/nextTick 순서, I/O 콜백 안팎의 Immediate 등록, 동기 반복문이 예약된 콜백에 미치는 영향.
- 환경 (Node.js 버전, OS, ESM 여부): Windows, Node.js v24.14.0(에이전트가 확인), package.json의 type은 module.
- 실행 명령 / 조건: `node experiments/event-loop.js`. 타이머 콜백 내부 호출 → readFile 콜백 안팎 비교 → 읽기 콜백에서 eventLoopVer1() 호출 뒤 Date.now() 기준 약 2초 동기 반복문 추가.
- 예상 결과와 이유 (실행 전 사용자 답변 요약): 처음에는 Promise가 먼저 등록되므로 4가 먼저라고 예상. 설명 후 서로 다른 큐의 등록 순서와 처리 순서를 구분했다. 같은 마이크로태스크 큐 예제에서는 A 등록 → B 등록 → A 실행 중 C 등록 → B → C를 정확히 설명했다. 동기 반복문을 추가해도 I/O 콜백 안에서 등록한 Immediate 3이 타이머 2보다 먼저라고 예상했다.
- 관찰 결과 (사용자 보고): 타이머 내부 호출은 1 → 6 → 5 → 4 → 3 → 2. 읽기 콜백 밖의 Immediate와 읽기 완료 로그 비교는 Immediate → 파일 읽기 완료. 읽기 콜백에서 함수를 호출하고 바깥 Immediate를 유지한 경우 Immediate → 1 → 6 → 5 → 4 → 3 → 2. 약 2초 동기 반복문 추가 후 5, 4, 3, 2가 모두 지연됐다고 보고했다. 정밀 시간 측정은 하지 않았다.
- 차이의 원인 / 추가 확인: 마이크로태스크가 큐에 있는 상태와 그 큐를 처리 중인 상태를 구분했다. 콜백은 전달한 함수이며 readFile 호출 반환과 파일 읽기 완료는 별개다. poll/check는 이벤트 루프의 처리 구간이고 check는 반복해서 도달하므로 I/O 콜백 안에서 Immediate를 등록해도 실행 기회를 놓치지 않는다. 콜백 밖 Immediate의 한 번 관찰한 순서를 일반적인 보장으로 취급하지 않는다.
- 내 말로 설명한 결론 (사용자 답변 요약): Immediate는 등록 후 check에서 실행을 기다리므로 다음 코드는 계속 진행한다. 동기 작업 때문에 nextTick, Promise, Immediate, 타이머의 실행이 모두 지연된다.
- 코드 / 커밋 링크: [현재 실험 코드](../../experiments/event-loop.js). 코드 내용은 에이전트가 확인했으며 이번 결과를 별도로 재실행하지 않았다.

## 리뷰와 다음 단계

- 리뷰 내용: 등록과 실행, 서로 다른 큐와 같은 큐의 순서, I/O 콜백과 check 단계, 동기 작업 중 콜백 실행 지연을 설명·실험했다. 평소 확인 답변이며 마무리 Q&A 평가와 구분한다.
- 추가 비교: 사용자는 동기 반복문을 setTimeout(..., 2000) 등록으로 바꾸면 5 → 4 → 3 → 2가 그 타이머 때문에 지연되지 않는다고 예측했고, 실행 안내 후 확인했다고 답했다. 에이전트는 실제 코드 교체와 바깥 Immediate 제거를 확인했다. 추가 실행의 전체 로그나 정밀 시간은 제공되지 않았다. 2초 지연의 기준은 2 출력 완료가 아니라 setTimeout 호출 시점이라고 설명했다.
- Promise 내부 동기 계산 비교: V8, libuv, Worker Pool의 역할과 파일 작업·JavaScript 콜백의 실행 위치를 설명했다. 사용자는 Promise 콜백의 반복문 실행 중 Immediate가 끼어들 수 없다고 예측했다. 현재 코드에서 읽기 콜백은 eventLoopVer1() 호출 후 계산용 Promise 콜백을 등록한다. 사용자 제공 출력은 1 → 6 → 5 → 4 → 계산 시작 → 계산 끝 → 3 → 2이며, 마이크로태스크 큐를 비운 뒤 나머지 콜백이 실행됐다고 설명했다. 에이전트는 코드 구조를 확인했고 별도로 재실행하지 않았다.
- 남은 질문: 파일 I/O와 JavaScript 콜백의 실행 위치, ESM 최상위와 타이머·I/O 콜백 실행 맥락을 후속 학습에서 독립적으로 다시 설명할 수 있는지 확인한다.

### 지금까지 다룬 내용과 사용자 답변

- 사용자는 처음에 작성 순서대로 출력될 것으로 예상했다. 최초 예제에서 동기 시작 → 동기 끝 → Promise → nextTick → setImmediate → setTimeout 출력을 관찰했다고 보고했다. 마지막 두 타이머 관련 출력 순서를 항상 보장된 규칙으로 취급하지 않는다.
- Promise.resolve()의 이행과 .then 콜백 실행은 다르며, 이미 이행된 Promise의 .then도 콜백을 즉시 호출하지 않는다는 점을 설명했다.
- 함수마다 마이크로태스크 큐가 생기는 것은 아니다. 이 단일 스레드 예제에서는 중첩 함수들도 같은 큐에 작업을 추가한다.
- 타이머 등록과 동기 계산을 비교했다. setTimeout은 등록 후 바로 반환하지만, 동기 반복문은 실행 중인 JavaScript 스레드를 차지한다. Promise나 타이머로 감싸도 긴 동기 계산이 시작되면 다른 요청의 JavaScript 처리를 막는다.
- 콜백 내부의 예약 코드는 해당 콜백이 실제 실행되어 그 줄에 도달해야 실행된다. 사용자는 처음에는 내부 작업이 미리 등록된다고 생각했지만, 이후 등록 시점과 큐 뒤에 추가되는 순서를 맞게 예측했다.
- 콜백의 종류는 등록 API로 결정된다. .then/queueMicrotask는 마이크로태스크, process.nextTick은 별도 nextTick 큐, setTimeout은 타이머다. 바깥 콜백의 종류가 안쪽 콜백에 상속되는 것은 아니다.
- ESM 최상위 실행은 이미 마이크로태스크 처리 흐름 안에 있다는 점을 설명했다. ESM 전용 큐가 따로 있다는 뜻이 아니다. 이미 마이크로태스크를 처리 중이면 추가된 마이크로태스크를 처리하고 나서 nextTick으로 넘어간다. 일반 타이머 콜백 반환 후에는 nextTick을 먼저, 마이크로태스크를 그다음 처리한다.
- 마지막 확인: 바깥 마이크로태스크에서 A 출력 → nextTick B 등록 → 마이크로태스크 D 등록 → C 출력이면 A,C,D,B라고 답했다. 바깥을 타이머 콜백으로 바꾼 예제에서는 A,C,B,D라고 맞게 답했다. 이는 대화 중 예측이며 실제 실행 검증이나 독립적인 전체 이해도 평가와 구분한다.

### 재개할 정확한 지점

1. 학습 지침과 이 기록을 읽고 experiments/event-loop.js의 최신 내용을 확인한다. 종료 시 파일은 eventLoopParent가 비어 있고 eventLoopVer1을 최상위에서 직접 호출하는 형태다. 이전 대화의 중첩 함수 버전과 다르므로 예전 구조를 가정하지 않는다.
2. 마지막으로 제안한 활동은 최상위 직접 호출을 타이머 콜백 내부 호출로 옮겨 Promise와 nextTick 순서를 비교하는 것이다. 최신 코드에 맞춰 eventLoopVer1() 호출을 setTimeout(() => { eventLoopVer1(); }, 0)로 바꾸는 실험을 안내한다.
3. 먼저 사용자에게 Promise 로그 4와 nextTick 로그 5의 순서를 예측하도록 한 가지 질문을 한다. 아직 이 실제 파일 변경 실험의 예측 답변과 실행 결과는 받지 않았다. 정답을 미리 공개하지 않는다.
4. 사용자가 직접 수정·실행한 뒤 결과를 함께 분석한다. Node.js 버전과 OS도 확인해 기록한다. 이후 I/O 콜백에서의 비교, setImmediate와 setTimeout의 차이 등 미학습 항목으로 이어간다.

### 진행 방식

- 설명만으로 끝내지 말고 현재 코드에 연결된 질문 또는 작은 실험 하나로 이어간다. 이미 이해한 동일 질문을 반복하지 않는다.
- 사용자가 혼동하면 새 예외를 추가하기 전에 현재 실행 중인 함수, 등록되는 함수, 각 큐를 구분한다. 특히 “동기 코드가 끝나면”만으로 모든 실행 맥락을 설명하지 않는다.
- 사용자가 다른 PC로 이동하기 위해 중단했다. 평가를 강제하지 않고 이 지점부터 재개한다. 실제 학습 시간, Node 버전, 추가 실행 결과는 미확인이다.
