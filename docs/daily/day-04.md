# Day 4 · Stream과 메모리

## 복습 결과 · 2026-11-17

- 질문: data마다 chunks.push만 하는 코드에서 heapUsed는 일정하고 arrayBuffers가 증가하는 이유.
- 첫 답변: 디스크 쓰기가 수신보다 느려 쌓인다고 해석하고 전송 속도 조절 제안. 코드에는 쓰기가 없으므로 해당 원인 분석은 재학습 필요(0). 실제 쓰기가 있는 경우의 타당한 가설과 구분한다.
- Buffer 참조를 계속 보관하는 코드와 메모리 지표 범위를 설명했다. 속도를 절반으로 줄여도 같은 파일을 모두 보관하면 최종 보관량은 같다고 후속 답변했다.
- 에이전트가 디스크 쓰기 없는 원인 분석에서 pipeline 파일 저장 해법으로 전환하며 전제를 누락했고 사용자가 지적했다. 이 혼란을 사용자 이해도 부족으로 평가하지 않는다.
- 현재 바이트 수 응답 목적이라면 chunk.length만 누적하고 배열 보관·concat을 없애면 된다고 설명. 전체 내용 보관에는 크기·동시 수 제한이 필요하고, 조각별 처리에서는 계속 보관하지 않도록 구분했다. 사용자는 이해했다고 답했으며 독립 재확인 없음.
- 복습 종료, 실제 코드 변경·새 실험 없음. Notion 저장·재조회 확인.

## 질문 방식 피드백 · 2026-11-16

- 사용자는 “어떤 관점에서 비교하는가”, “질문이 계속 추상적이며 잘못된 방향 같다”고 지적했다. 직전 질문은 readFile과 Stream의 메모리를 공정하게 비교하려면 같은 파일 외에 무엇을 통제해야 하는지 묻는 내용이었다. 판단할 메모리 지표와 구체적인 비교 상황을 충분히 제공하지 않았다.
- 지속 적용할 원칙은 학습 지침의 대화 흐름 유지 절에 반영했다. 비교 목적·대상·조건을 설명하고 구체적인 상황 하나로 질문한다. 개념을 설명하기 전에 광범위한 실험 설계를 요구하거나, 확인 질문을 계속 이어 붙이지 않는다.
- 직전까지 다룬 내용은 요청별 createReadStream의 Buffer, OS 파일 캐시와의 차이, 느린 클라이언트 B에 연결된 읽기만 조절하는 백프레셔다. 사용자는 B의 파일 읽기만 늦추면 된다고 답했다. 실험 실행이나 마무리 Q&A 완료로 기록하지 않는다.
- 재개할 때는 서버 다운로드 메모리 비교의 목적과 조건을 먼저 설명한다. 직전의 추상적인 질문에 대한 답변을 요구하지 않는다.
- 이번 피드백은 로컬 지침과 Day 4 기록에 저장했다. 2026-11-16 Notion 기존 페이지에 질문 방식 피드백·Day 3 마무리 결과·Day 4 진행 지점을 반영하고 재조회로 확인했다.

## 용어 범위 추가 피드백 · 2026-11-16

- 사용자는 heapUsed·arrayBuffers·rss 모두 서버 메모리 지표인데 “서버 메모리 사용량”을 무엇으로 한정하는지 질문했다. 에이전트가 상위 표현을 사용하면서 rss를 기대 답으로 삼은 점을 바로잡았다.
- 학습 지침에 측정 대상·범위 명시, 지표의 포함·중첩 관계 설명, 다른 지표에도 같은 원칙 적용을 추가했다. 이후에는 “서버 프로세스가 RAM에 올려 사용하는 메모리(rss)”처럼 구체적으로 표현한다.
- 직전 500MB 다운로드의 8/9MB heapUsed, 1/501/3MB arrayBuffers, 50/555/58MB rss 표는 설명용 가상 수치다. 실제 측정 결과로 기록하지 않는다.
- 이번 추가 피드백은 로컬에 반영했다. 이전 Notion 동기화 이후 추가된 내용이며 아직 동기화하지 않았다.

## 기반 원리 설명에 대한 선호 · 2026-11-16

- 마무리 전에 사용자는 이번 Day 4의 네트워크·운영체제 관점 설명을 좋은 방향으로 평가했다. Node.js 밖의 관련 주제도 더 자세히 설명하며 질의응답하기를 원한다고 명시했다.
- 학습 지침에 지속 선호로 반영했다. 소켓 버퍼·TCP, OS 파일 캐시, 메모리 할당과 회수 등을 Node.js 동작과 연결하고, 계층별 역할과 인과관계를 상세히 설명한다. 확장 범위와 종료 지점을 먼저 안내한다.
- Day 4 마무리 질문 3개에 답변은 받았으며 사용자가 추가 학습 방식 논의를 요청했다. 이 기록 시점에 마무리 결과 정리와 Notion 동기화는 아직 완료하지 않았다.

## 직전 세션 재확인 · 2026-11-17

- 11월 16일 실제 대화에서 Day 4를 OS·네트워크 관점으로 다시 설명한 뒤 사용자가 Day 5로 이동을 요청했음을 확인했다. 이전 문서의 시작 전·Q&A 미시작 표시는 최신 진도를 나타내지 않는다.
- OS 페이지 캐시와 요청별 Node.js Buffer, 소켓 버퍼를 구분했다. 같은 파일이 OS 캐시에 있어도 별도 readFile 결과 Buffer가 생략되지는 않는다고 사용자가 답했다.
- 페이지 캐시·dirty page, 파일 쓰기 완료와 저장 장치의 내구성 보장 차이, TCP 수신 윈도우와 혼잡 제어, write(false)·drain·finish·ACK·클라이언트 저장 완료의 범위를 설명했다. 설명 전체를 독립 숙달로 간주하지 않는다.
- 사용자가 배경 설명이 Sprint에서 멀어진다고 지적해 현재 buffer.push 코드의 전체 보관과 Stream의 흐름 조절·참조 해제로 돌아왔다. 기반 원리 설명을 유지하되 현재 학습 범위로 돌아오는 종료 지점이 필요하다.
- 마무리 답변을 받았다는 기존 기록과 직전 세션의 피드백을 확인했다. 전체 보관·조각 처리 차이와 높은 rss만으로 누수를 확정할 수 없다는 점은 설명했으며, heapUsed/arrayBuffers만으로 읽기·소비 정상 여부를 추론하지 않도록 보완했다. 원래 질문별 답변 전체는 이번에 복원하지 않았으므로 개별 점수를 만들지 않는다.
- 새 실행은 하지 않았다. 기존 32MiB concat 실험은 Notion 기록에 있고, 500MB readFile/pipeline 비교는 미수행이다. 다음은 사용자 요청에 따른 Day 1~5 복습이다.
