# Day 5 · Backpressure와 오류

## 복습 결과 · 2026-11-17

- 질문: 임시 파일로 스트리밍 업로드 중 연결이 끊겼고 쓰기 데이터가 남은 경우 정리 순서. 파일 저장을 추가한 조건임을 명시했다.
- 첫 답변: 남은 데이터를 모두 임시 파일에 쓴 뒤 삭제한다고 설명. 정리 후 삭제 방향은 이해했지만 전체 쓰기 완료가 필요하다고 해석하여 부분 이해(1).
- 보완: 버릴 파일에 남은 데이터를 모두 쓸 필요는 없다. 중단 요청 → 실제 쓰기 종료와 파일 핸들 정리 확인 → 삭제. 이미 OS에 제출된 쓰기 일부는 완료될 수 있음을 구분했다.
- 후속 답변: 요청이 제대로 중단됐는지 확인하고 파일 삭제를 진행해야 한다고 설명. 교정 후 종료 확인 필요성을 재설명한 것으로 기록하며 독립 숙달로 올리지 않는다.
- Day 1~5 복습 종료. 강점: 메인 스레드 블로킹 원인, 저장 성공 후 응답, 확장 시 DB 병목 검토. 다시 볼 개념: 현재 코드의 Buffer 보관·메모리 지표, 중단 요청과 실제 자원 정리 완료의 차이.
- 다음: Day 6 정상 종료. 앞서 제시한 다운로드 남은 시간 3초·유예 10초 질문은 미응답이다.
- 새 실험·구현 없음. 실험 완료 체크 유지. Notion에 결과 저장·재조회 확인.

## 대화 기반 진행 기록 · 2026-11-17

근거: 11월 16일 직전 세션의 실제 대화와 11월 17일 현재 대화. 아래는 답변 요약이며 새 실행·측정 결과가 아니다. 서버 코드는 /health 및 업로드 본문 Buffer 수집·바이트 수 응답 단계로, 파일 저장·다운로드는 미구현이다.

### 전송 실패와 취소

- 200 헤더 수신과 본문 수신 완료를 구분했다. 사용자는 200 이후 실패할 수 있으므로 상태만으로 성공 판단하면 안 된다고 설명했다.
- createReadStream/pipe 호출 바깥 try/catch는 나중 error 이벤트를 처리하지 못하며, Promise pipeline을 await하면 거부를 catch에서 처리할 수 있다고 설명했다. await 제거 시 나중 거부를 catch가 처리하지 못한다고 사용자가 답했다.
- 헤더 전송 후에는 상태를 500으로 바꿀 수 없으며 오류 JSON을 파일 본문에 덧붙이지 않는다. pipeline 실패로 응답도 파괴됐을 수 있어 항상 오류 응답을 보낼 수는 없다.
- 사용자는 업로드 저장 성공 응답과 다운로드 본문 전송의 차이를 질문한 뒤, 다운로드는 처리 결과 자체가 응답이라고 정리했다. 클라이언트의 본문 수신과 파일 저장 완료도 구분해 설명했다.
- 다운로드 취소 시 해당 요청의 읽기 스트림·연결만 정리하고 서버 원본 파일과 다른 요청은 유지한다. 사용자는 계속 읽으면 불필요한 메모리 사용과 불확실한 정리 시점이 생긴다고 답했다. 전체 파일이 반드시 쌓이는 것은 아니며 버퍼 보관·흐름 조절 방식에 따라 다르다고 보완했다.
- 업로드 취소 시 임시 파일 삭제 전에 무엇을 확인하는지는 모르겠다고 답했다. 중단 요청 → 실제 쓰기 종료·파일 핸들 정리 확인 → 임시 파일 삭제 순서를 설명했다.
- 타임아웃도 같은 사례라고 연결하고 추가 확인이 필요하다고 답했다. 확인 후 중단이 아니라 중단 요청 후 실제 종료 확인이라는 순서를 교정했다. 교정 후 독립 확인은 하지 않았다.

### 임시 파일 삭제 실패

- 삭제 실패가 설계 오류인지 질문했다. 쓰기는 종료됐지만 파일이 남은 상태를 구분하고, 정상 목록·다운로드에서 제외, 실패 원인과 경로 기록, 원인 해결 후 재정리를 설명했다.
- 점검·정리하지 않으면 미삭제 파일이 계속 쌓인다고 사용자가 설명했다. 이 가정에서는 주로 디스크 공간 점유 문제이며 새 업로드 실패로 이어질 수 있음을 연결했다.
- 전체 요청·프로세스 이력 관리가 과도하지 않은지 질문했다. 단일 프로세스가 독점하는 전용 임시 폴더를 요청 수신 전에 청소하는 방식을 설명했다. 재시작 전에는 잔여물을 치우지 못한다는 한계도 설명했다.
- 실행 중 청소의 선택지로 현재 사용 중인 경로만 Set에 등록하는 방식을 소개했다. 쓰기 시작 전 등록, 실제 종료·핸들 정리 후 해제, 고유 경로 사용이 전제다. 다중 프로세스 공유 폴더에는 이 목록만으로 충분하지 않다. 구현한 정책이 아닌 설명용 선택지이며 사용자는 이해했다고 답했다.

### 학습 방식과 다음 지점

- 업로드/다운로드 방향과 서버/클라이언트 관점을 명확히 표시한다. 예시 폴더 이름 때문에 맥락을 혼동한 것을 이해도 부족으로 평가하지 않는다.
- 사용자는 설명만 이어갈 때 질의를 요청했지만, 같은 결론을 반복 질문하는 것도 지적했다. 새 대응 방법은 먼저 설명하고 필요한 적용 질문만 한다.
- Day 6 정상 종료 도입 설명과 예측 질문은 제시됐으나 미응답이다. 사용자 요청으로 Day 6 진행을 보류하고 Day 1~5 복습을 먼저 진행한다.
- 복습 계획: Day별 핵심 질문 한 개씩 총 5개, 답변에 따라 필요한 부분만 보완. 한 번에 한 질문씩 하고 각 Day 문서에 첫 답변과 도움 후 답변을 구분해 기록한다. 현재 Day 1 질문 제시 예정, 전부 미평가.
