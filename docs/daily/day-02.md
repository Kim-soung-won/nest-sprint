### 첫 실습: 요청 하나에 응답하기

`createServer(handler)`는 HTTP 서버를 만들고 요청을 처리할 함수를 등록한다. `handler(req, res)`는 요청마다 호출되며, `req`는 받은 요청, `res`는 보낼 응답이다. `req.url`로 요청 경로를 확인하고 `res.end("ok")`로 응답 본문을 보내면서 응답을 끝낸다. 서버의 `listen(3000, "127.0.0.1")`은 로컬 3000 포트에서 연결을 받기 시작한다.

1. 시작 파일의 안내대로 요청 경로를 출력하고 `ok`를 응답하는 서버를 직접 구현한다.
2. 터미널 A에서 `npm run experiment:cpu-blocking`을 실행한다.
3. 터미널 B에서 `curl -i http://127.0.0.1:3000/fast`를 실행한다.
4. 서버의 경로 로그와 curl의 상태 코드·본문을 확인한다. 종료할 때는 터미널 A에서 Ctrl+C를 누른다.

### 이후 실험 순서

첫 응답 확인 → `/fast` 즉시 응답과 `/cpu` 약 3초 동기 계산 구현 → `/fast` 단독 기준값 측정 → `/cpu` 계산 중 `/fast` 요청 → 타이머 지연으로 교체해 비교 → async 함수 안의 동기 계산 비교. Worker Thread 구현은 선택 과제다.

시간은 curl의 `-w '\n전체 시간: %{time_total}s\n'`으로 측정한다. CPU 계산 시작 로그를 확인한 뒤 별도 터미널에서 `/fast`를 요청해 실제로 겹쳤는지 확인한다. `/fast` 지연은 요청을 보낸 시점에 따라 달라지므로 항상 3초라고 가정하지 않는다. 타이머 지연은 실제 파일 I/O가 아니라 기다리는 동안의 동작을 비교하기 위한 조건이다.

| --- | --- | --- | --- |
| /fast 단독 | 미작성 | 미측정 | 미관찰 |
| 동기 CPU 계산 중 | 미작성 | 미측정 | 미관찰 |

## 현재 진행 · Worker 풀 실험

이 절은 아래 준비 당시 기록보다 최신이다. Notion에는 아직 동기화하지 않았다.

- 사용자 관찰: 메인 스레드의 3초 동기 계산 중 0.5초 뒤 보낸 `/fast`는 2.497539초 걸렸다. 타이머 대기로 바꾸면 지연이 겹치지 않았고, async 함수 안의 동기 계산에서는 다시 지연됐다고 보고했다.
- 요청마다 Worker를 생성한 버전: 사용자 `/fast` 측정값은 0.001834초였으며 `/cpu`의 응답보다 먼저 도착했다.
- 사용자 이해 확인: 동기 계산의 실행 위치를 Worker로 옮겨 메인 스레드가 다른 요청을 처리할 수 있다고 설명했다. Worker 개수와 생성 비용, 대기 중 메인 스레드 점유 여부에 대한 질문을 바탕으로 풀과 작업 큐를 소개했다.
- 현재 구현: [서버](../../experiments/cpu-blocking.js), [Worker 풀](../../experiments/worker-pool.js), [계산 Worker](../../experiments/worker.js). Worker 2개를 재사용하며 FIFO 대기 큐는 10개까지 보관한다. 초과 작업은 503, Worker 오류는 풀 중단 및 미완료 작업 실패로 처리한다.
- 에이전트 검증: 별도 포트 13002에서 `/cpu` 13개 동시 요청. 2개 실행·10개 대기·1개 503을 확인했다. 첫 두 응답은 약 3초, 다음 두 응답은 약 6초에 완료됐고 Worker 준비 로그는 총 2개였다. 0.5초 뒤 요청한 `/fast`는 2ms, HTTP 200이었다. 검증 서버는 종료했다. 문법 검사와 `git diff --check`도 통과했다.
- 로그: `ready`는 Worker 준비, `start`는 작업 배정, `queued`는 작업 대기, `done`은 계산 완료다. 작업 번호로 요청에 연결된 Promise를 완료한다.
- 학습용 한계: Worker 자동 복구, 연결 종료 시 계산 취소, 정상 종료 절차는 구현하지 않았다. 현재 Worker는 고정된 약 3초 반복문만 수행한다.
- 다음 활동: 서버 재시작 후 `/cpu` 3개를 동시에 보내고 `/fast`도 요청한다. 세 번째 계산이 큐에서 대기하다 먼저 끝난 Worker에 배정되는지 로그로 확인한다. 사용자의 풀 실험 결과와 마무리 Q&A는 아직 확인 전이다.

- 사용자는 Worker 풀 실험이 잘 동작한다고 확인했다. 구체적인 추가 로그나 측정값은 제공하지 않았다.

- 첫 질문(설명): 메인 스레드에서 실행하는 async 함수의 계산과 Worker 풀에 맡긴 계산은 모두 await로 기다리는데, 왜 전자는 /fast를 지연시키고 후자는 다른 요청을 처리할 수 있는가? await 전후의 실행 위치와 동작으로 설명한다.
