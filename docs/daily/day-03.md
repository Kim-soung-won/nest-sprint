## 학습 방식과 재개 지점 · 2026-11-13

- 사용자 요청: 직접 코딩을 계속 수행하는 방식보다 개념적인 공부가 중요하므로 이를 명시한다. 학습 지침에 개념 우선, 직접 구현은 사용자 희망 시 진행, 코드·실험은 이해를 돕는 수단이라는 원칙을 반영했다.
- 지금까지 다룬 개념: req.url은 출발지가 아닌 요청 경로·쿼리이며, node:http에는 기본 req.body가 없다. 요청 본문을 data의 Buffer 조각으로 받고 end에서 합친다. 등록과 수신 완료를 구분하고, res.end는 JavaScript 함수 자체를 종료하지 않음을 확인했다.
- 사용자 확인: /health 응답, 업로드 본문 바이트 수 응답이 동작했다고 보고했다. UTF-8의 '안녕'은 2가 아니라 6바이트라고 스스로 정정한 뒤 실행 결과도 확인했다.
- 당시 다음 개념(이후 아래 「개념 대화 이어서」 절에서 진행함): 업로드한 바이트를 파일에 저장하는 흐름과 저장 경로의 의미. 경로 검증 코드를 직접 작성하라는 과제는 이어가지 않는다. 본문 수신 완료, 파일 쓰기 완료, HTTP 응답 시점의 차이를 중심으로 설명한다.
- 파일 저장·크기 제한·파일 목록·다운로드는 아직 구현 및 검증하지 않았다. 마무리 Q&A는 미진행이다.

## 개념 대화 이어서 · 2026-11-13

이 절이 위 재개 지점보다 최신이다. Codex 세션의 대화 이력(2026-11-13 16:36~17:45 KST)을 조회해 반영했다. 이 구간은 설명과 질의응답만 진행했으며 `src/server.js`는 바뀌지 않았다. 파일 저장(writeFile)은 설명용 예시 코드로만 다뤘고 구현하지 않았다.

### 다룬 개념

- 세 시점의 구분: 요청 본문 수신 완료(req의 end, 데이터는 메모리에 있음) → 파일 쓰기 완료(await writeFile 이후) → 응답 전송(res.end 호출이 곧 클라이언트 수신 완료는 아님).
- 저장이 성공한 뒤에만 성공 응답을 보낸다. 실패하면 catch에서 500으로 응답한다.
- 멱등성: 같은 요청을 반복해도 최종 상태가 같은 성질. 서버는 저장에 성공했지만 클라이언트가 응답을 못 받으면 재시도할 수 있으므로 필요하다. 동시 요청 간 충돌까지 해결하지는 않는다.
- 메모리: 현재 코드는 본문 전체를 메모리에 보관한다. Buffer.concat은 새 Buffer에 복사하므로 합치는 순간 본문의 약 2배가 필요할 수 있다. 크기 제한은 메모리 보호 장치이며, data마다 누적 크기를 검사하고 초과하면 413으로 거절한다. 오류 응답을 보내는 것과 요청 수신을 중단하는 것은 별개다.
- 요청당 크기 제한과 동시 처리 수 제한은 역할이 다르다(10MB × 동시 100개 ≈ 1GB).
- Content-Length는 본문 크기를 미리 알려 조기 거절에 쓸 수 있지만, chunked 전송처럼 전체 크기를 모르는 요청도 있어 수신 중 누적 검사가 함께 필요하다. Content-Length가 있어도 data 이벤트는 여러 번 발생할 수 있다. (에이전트가 RFC 9110·9112를 확인하며 설명)
- Nginx의 client_max_body_size도 Content-Length 비교와 chunked 본문 누적 검사를 모두 수행한다. (에이전트가 공식 문서와 소스를 확인하며 설명)
- 버퍼와 백프레셔: 네트워크 → OS 소켓 수신 버퍼 → Node.js 스트림 버퍼 → 파일 쓰기. 버퍼는 일시적인 속도 차이를 흡수하고, 백프레셔는 차이가 지속될 때 흐름을 조절한다. 실제 전송량 조절은 TCP 수신 윈도우로 OS가 수행하며, 애플리케이션은 읽는 속도와 크기 제한으로 관여한다. Node.js Stream에서의 동작은 Day 4~5에서 다룬다.
- 미완성 파일: 임시 이름으로 쓰고, 정상 수신과 쓰기 완료를 모두 확인한 뒤 최종 이름으로 바꾼다. 중단·실패 시 임시 파일을 정리한다.
- 메서드의 안전성(safe)과 멱등성(idempotent)은 다른 성질이다. DELETE는 안전하지 않지만 멱등적으로 설계할 수 있다.
- 상태 코드와 응답 본문은 별개다(201, 400, 404, 413, 500).

### 사용자 답변과 질문

평소의 확인 질문이며 마무리 평가가 아니다.

| 질문 | 사용자 답변 | 비고 |
| --- | --- | --- |
| 저장 실패인데 saved를 받는 상황을 피하려면 저장과 성공 응답의 관계는? | "멱등성?" | 질문이 추상적이었다고 에이전트가 인정하고, 저장 성공 후 응답이라는 순서와 멱등성의 차이를 설명했다. 사용자가 독립적으로 답한 것으로 기록하지 않는다. |
| 같은 경로에 덮어쓰기와 요청마다 새 파일 중 멱등적인 쪽은? | 덮어쓰는 방식 | 정확 |
| 1GB 업로드 시 저장 전 내용은 어디에 보관되는가? | "메모리? 디스크?" | 확신하지 못함. 에이전트가 메모리이며 concat 복사 비용을 설명 |
| 크기 검사는 end에서 한 번과 data마다 누적 중 어느 쪽이 메모리를 보호하는가? | 받을 때마다 검사하는 쪽 | 정확 |
| 10MB 업로드 100개 동시 진행 시 필요한 메모리는? | 답하지 않고 질문으로 전환 | 에이전트가 이후 약 1GB라고 설명 |
| 수신이 디스크 쓰기보다 빠르면 아직 쓰지 못한 데이터는? | 버퍼에 저장된다(네트워크 기초에서 배움) | 맞음. 에이전트가 버퍼의 위치와 백프레셔를 덧붙임 |
| 저장 중인 파일과 저장이 끝난 파일을 어떻게 구분할까? | 다음 청크를 기다리는 중인지 체크하는 부분이 있지 않나 | 질문 의도와 다른 답. 임시 파일 후 이름 변경 방식은 에이전트가 설명했고 사용자는 이해했다고 답함 |
| 파일 삭제를 GET /delete로 만들면? | 조회를 위해 호출했는데 의도하지 않은 동작이 발생한다 | 정확 |
| 같은 내용을 덧붙이는 요청은 멱등적인가? | 아니다, 같은 내용이 두 번 덧붙는다 | 정확, 이유 포함 |

사용자가 먼저 꺼낸 질문:

- 네트워크 헤더에 요청 크기를 담지 않는가 → Content-Length와 chunked 전송.
- Nginx의 본문 크기 제한은 무엇을 검사하는가 → client_max_body_size.
- 실제 요청 헤더(Accept: text/event-stream, Content-Type: multipart/form-data)는 어떤 유형인가 → 본문은 multipart, 응답은 SSE를 원하는 요청. multipart의 부분과 chunked의 조각은 다른 개념. 사용자가 여기서 중단하고 원래 흐름으로 돌아갔으므로 더 진행하지 않았다.
- 백프레셔는 서버가 클라이언트에 이벤트를 보내는 것인가 → 애플리케이션 이벤트가 아니라 TCP 수신 윈도우. 사용자는 "OS 레벨이라 애플리케이션이 관여할 바가 아니다"라고 정리했고, 에이전트가 TCP 제어는 OS 담당이 맞지만 애플리케이션도 읽는 속도와 크기 제한으로 관여한다고 보완했다.

### 재개 지점

- 답변 대기 중인 질문: 서버가 404나 500으로 응답했을 때 `await fetch(...)`는 그 이유만으로 catch로 들어가는가? 사용자의 마지막 입력은 "어" 한 글자에서 끊겼고 답변으로 보지 않는다. 다시 물을 때 정답을 함께 공개하지 않는다.
- 그다음: 상태 코드와 본문의 일치, 저장 경로의 의미와 파일명 검증 개념, /files·/download 흐름.
- 다시 짚을 지점: 저장 성공과 성공 응답의 순서, 미완성 파일의 노출 방지(둘 다 에이전트 설명 후 이해했다고 답한 상태), 백프레셔에서 애플리케이션의 역할.
- 미구현·미검증: 파일 저장, 크기 제한, 파일명·경로 검증, /files, /download/:name, /error. 마무리 Q&A는 미진행.
